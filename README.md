# 抢地盘 Paint Rush

**在线试玩：https://paint-rush.onrender.com**

一个浏览器里的实时 1v1 涂色对战：两个人在 16×16 的格子上跑，走过的格子染成自己的颜色，也可以踩上对手的格子把它抢回来。60 秒后占地多的人获胜。无需注册，发一个链接就能对战。

> Render 免费套餐闲置约 15 分钟后会休眠，第一次打开可能要等 30 秒左右，之后就是正常速度。

---

## 1. 两个人怎么开始一局（30 秒）

1. **A** 打开 https://paint-rush.onrender.com ，点"创建房间，邀请好友"。
2. A 在大厅里点"复制邀请链接"，发给 **B**。也可以直接告诉 B 4 位房间码。
3. **B** 打开链接，点"加入房间"。两边的大厅都会实时出现对方。
4. A（房主）点"开始游戏"，两边同时出现 3-2-1 倒计时。
5. 用方向键或 WASD 移动。60 秒后双方看到同一个结算结果，都点"再来一局"就能开始下一局。

一个人也能测试：在同一个浏览器里开两个标签页（或者一个普通窗口加一个无痕窗口），分别扮演 A 和 B 即可。每个标签页是独立的玩家身份。

## 2. 本地运行

需要 Node.js 18 或更高版本。

```bash
npm install
npm run dev                    # 前端 http://localhost:5173（热更新），后端 :3000
```

生产模式（与线上一致，一个进程同时提供页面和 WebSocket）：

```bash
npm run build && npm start     # http://localhost:3000
```

### 自动化验收脚本

每个开发阶段都配有一个脚本，用真实的 Socket.IO 客户端模拟两个玩家，跑完整个流程。可以对本地或线上地址运行：

```bash
npm run smoke    -- http://localhost:3000   # 骨架：两个客户端通过 WebSocket 连上
npm run accept:2 -- http://localhost:3000   # 房间：创建、加入、满员、错误码、非房主不能开始、两端倒计时同步（15 项）
npm run accept:3 -- http://localhost:3000   # 玩法：完整打一局，两端快照逐帧一致、连按不加速、乱序和重复包被丢弃、碰撞、结算一致（16 项，约 70 秒）
npm run accept:4 -- http://localhost:3000   # 生命周期：刷新回原位、掉线 15 秒判负、主动离开、再来一局、中途加入、房主转移、重复连接（22 项，约 90 秒）
npm run latency  -- http://localhost:3000   # 诊断：测量按键到服务器快照中出现位移的延迟
```

把地址换成 `https://paint-rush.onrender.com`，就是对线上环境验收。以上脚本在本地和线上都已全部通过。对线上验收时请依次运行，不要并行：几套脚本同时跑时，网络抖动可能导致少数时序类检查误报，服务器本身的负载很低。

## 3. 架构

```
 浏览器 A                                   浏览器 B
 ┌───────────────────┐                     ┌───────────────────┐
 │ 键盘 → 方向意图     │                     │ 键盘 → 方向意图     │
 │ {seq, dir}        │                     │ {seq, dir}        │
 │ Canvas 渲染 + 插值  │                     │ Canvas 渲染 + 插值  │
 └───┬───────────▲───┘                     └───┬───────────▲───┘
     │ input     │ snapshot / room / over      │ input     │
     ▼           │      (Socket.IO / WebSocket)▼           │
 ┌───────────────┴─────────────────────────────────────────┴───┐
 │ Node.js 单进程（Express 托管前端 + Socket.IO）                  │
 │                                                             │
 │  rooms.ts  房间与玩家生命周期：joinRoom / markDisconnected /     │
 │            removePlayer / voteRematch，状态全部在内存里          │
 │  game.ts   10 Hz tick：移动、碰撞、涂色、计时、结算（纯规则函数）   │
 │  index.ts  HTTP 接口、Socket 事件、输入校验与限流、广播           │
 └─────────────────────────────────────────────────────────────┘
               shared/protocol.ts：前后端共用的事件和类型定义
```

| 部分 | 技术 | 说明 |
|---|---|---|
| 前端 | TypeScript + Vite，原生 DOM + Canvas 2D，不用框架 | 页面只有首页、房间（大厅、倒计时、对局、结算）和浮层，用框架反而更重 |
| 实时通信 | Socket.IO（只用 WebSocket 传输） | 自带房间广播、心跳和自动重连 |
| 后端 | Node.js + Express + Socket.IO | Express 同时托管前端构建产物，单服务部署，没有跨域问题 |
| 协议 | `shared/protocol.ts` | 前后端共用一份类型，事件写错名字或字段时编译就会报错 |
| 部署 | Render Web Service（新加坡） | 支持长连接 WebSocket，部署一个服务即可 |

## 4. 题目中四个思考点的回答

### 4.1 进入游戏的体验：让两个人尽快开始第一局

- **不需要账号**。首页会自动生成一个随机昵称（如"淡定的狐狸"），可以修改，保存在 localStorage。
- **用链接邀请**。创建房间后得到一个 4 位房间码和链接 `/r/ABCD`。房间码去掉了 I、O、0、1 这类容易看错的字符。对方打开链接后，会先看到"好友邀请你加入"的确认卡片，可以在这里改昵称，点一下就入座。
- **从打开页面到开局，A 点两次（创建、开始），B 点一次（加入）**。
- **问题在进门前就提示**：打开链接时先查询房间状态。房间不存在或已满时，直接显示原因和"返回首页"按钮，不会让人进到一个空白页面。

### 4.2 核心玩法与产品反馈

- **规则一句话就能说清**："走过的格子变成你的颜色，60 秒后格子多的赢"。首页和对局页都写着这句话，不需要另外的教程。
- **操作**：方向键或 WASD，按住连续走，点一下走一格。倒计时期间就可以提前按住，开局瞬间就会出发。同时按住多个方向时，以最后按下的为准。切走窗口会自动松开所有方向，避免角色一直走。
- **对抗性**：可以踩掉对手的格子，所以不是各涂各的，而是会围绕地盘反复争夺。两人不能站在同一格，可以用身体挡住对方。
- **胜负明确**：结算由服务器给出，显示"你赢了 / 你输了 / 平局"、双方的百分比和格子数，以及结束原因（时间到或对手离开）。
- **游戏感**：
  - 棋盘：新涂的格子从中心"溅开"，角色在两帧之间平滑移动；倒计时期间就显示棋盘和双方出生点，自己头上有一个小标记。
  - 节奏：顶部实时显示双方占地百分比和比例条；最后 10 秒计时变红闪烁，并且每秒响一声。
  - 声音：倒计时、开局、涂色、抢到对手的格子、结算都有音效。音效全部用 Web Audio 现场合成，不加载任何音频文件，右上角可以关闭。
- **即时反馈**：按下方向键时，自己角色的眼睛和旁边的小箭头会立刻转向按键方向。这一步不需要等服务器回包，所以网络有延迟时也能马上知道"按键被接收了"。这只是视觉反馈，角色位置仍然以服务器为准，不会出现预测错误导致的回弹。

### 4.3 实时同步的质量

核心原则：**服务器决定一切，客户端只发送"我现在按着哪个方向"，并把服务器的结果画出来。**

| 问题 | 做法 |
|---|---|
| 状态由谁决定 | 服务器以 10 Hz 的固定频率推进（tick），计算移动、碰撞、涂色和计时，每个 tick 把完整的棋盘和位置广播给双方。客户端不做任何规则计算 |
| 网络延迟 | 角色在上一帧和当前帧之间插值，看起来是连续移动的；本地按键朝向即时显示（见 4.2）；倒计时和对局剩余时间以服务器下发的"剩余毫秒数"为准，不依赖两台电脑的时钟一致 |
| 重复操作 | 每条输入带递增序号 `seq`，服务器只处理比上次更新的输入。不管怎么连按，每个 tick 每人最多走一格，速度和网络、按键频率都无关（验收脚本测过：1 秒内狂按 200 次也不会加速） |
| 乱序 | 序号比已处理的旧的输入直接丢弃；客户端丢弃 tick 编号比当前旧的快照。因为每次都发完整快照，丢一帧下一帧就会自动恢复，不会越错越多 |
| 作弊 | 客户端无法提交坐标、格子或分数，只能提交上下左右四个方向之一；服务器校验越界、碰撞和速度，并限制每人每秒最多 20 条输入，超出的直接丢弃；昵称会过滤控制字符并截断，前端显示时会转义 |
| 两端结果不一致 | 不可能不一致：两端渲染的是同一份服务器快照，结算只以服务器下发的 `over` 为准。验收脚本会逐帧比对两端收到的快照（位置和棋盘），结果完全一致 |
| 碰撞公平性 | 两人同时想进同一格，或者一方想进另一方所在的格子时，**双方都不动**。规则对双方完全对称，不会因为谁的输入先到服务器，网络好的一方就占便宜 |

### 4.4 房间和玩家的生命周期

所有状态变化都集中在 `server/rooms.ts` 的四个函数里（`joinRoom`、`markDisconnected`、`removePlayer`、`voteRematch`），每次变化后广播完整的房间状态，客户端只根据收到的状态渲染。这样，刷新、掉线、离开、再来一局交叉发生时，只需要推理这四个函数。

| 场景 | 行为 |
|---|---|
| 刷新页面 | 每个标签页在 sessionStorage 里存一个私密的重连凭证（token），刷新后自动用它回到原座位，颜色、位置、已涂的格子都在，并直接回到当前阶段的画面（大厅、倒计时、对局或结算）。用 sessionStorage 而不是 localStorage，是为了让同一个浏览器里的两个标签页是两个独立的玩家 |
| 掉线或关闭页面 | 座位保留 15 秒，角色停在原地，对手看到"掉线中"；网络恢复后自动重连回到原位，页面顶部显示"正在重连"的提示条 |
| 掉线超过 15 秒或点"离开" | 大厅中：释放座位。倒计时或对局中：立即结算，剩下的一方获胜，结算里仍保留离开者的分数。结算页：剩下的一方看到"对手已离开"和"复制邀请链接"按钮 |
| 中途加入 | 有空座就能用同一个链接直接进来，比如对手离开后叫一个新朋友；满员时第三人看到"房间已满" |
| 房主离开 | 剩下的一方自动成为房主 |
| 再来一局 | 先点的一方显示"等待对方…"，另一方看到"对方已准备"；两人都点后，棋盘重置，进入新一局的倒计时 |
| 复制出相同的标签页 | 新页面接管座位，旧页面提示"已在别处打开"，避免两个页面同时控制同一个角色 |
| 空房间 | 无人满 60 秒后自动销毁 |

一个容易漏掉的细节：刷新后的新页面从 1 开始给输入编号，所以服务器恢复座位时会把这个座位的"已处理序号"清零，否则刷新后的每一个按键都会被当成旧消息丢掉。`accept:4` 专门覆盖了这个情况。

## 5. 取舍与已知限制

- **单实例，状态在内存里**：房间不写数据库，服务器重启或重新部署时，正在进行的对局会丢失（客户端会提示"房间不存在"）。对 1v1 的短局来说，这样换来的是零依赖和更简单的状态管理。
- **没有做完整的客户端预测**：自己的角色要等服务器回包才会移动，延迟大约是一次网络往返（RTT）加最多 100ms。正常网络下手感是可以的；网络很差时可能会觉得有点"发涩"。目前用"按键朝向即时显示"来缓解，见第 6 节。
- **Render 免费套餐会休眠**：闲置后第一次打开需要冷启动。
- **不支持手机和触屏**：按题目要求，只做桌面键盘操作。
- **创建房间接口没有限流**：理论上可以被刷出大量空房间，不过空房间 60 秒后会自动回收。
- **掉线时对局不暂停**：掉线一方在 15 秒内停在原地，对手可以继续涂色。这是有意的设计，暂停很容易被用来拖延时间。

## 6. 如果有更多时间

1. **完整的客户端预测和服务器校正**：自己的角色本地先走一格，服务器快照到达后再校正。难点在碰撞：预测可能和服务器的结果不一致，需要平滑回滚，避免画面闪烁。
2. **显示 Ping**，并在网络差时给出提示。
3. **观战**：满员时第三人以观众身份进入。
4. **随机匹配**，不需要找朋友也能玩。
5. **持久化和多实例**：房间状态放到 Redis，配合 Socket.IO adapter 支持水平扩展和不停机部署。

## 7. 开发过程

整个开发按阶段推进，每个阶段都有验收标准，并对线上地址跑一遍自动化验收：

| 阶段 | 内容 |
