# 决策记录

| # | 决策内容 | 理由 |
|---|---|---|
| 1 | 玩法定为 16×16 网格涂色对战，每局 60 秒 | 规则一句话就能说清，双方有直接对抗；状态很小，适合用全量快照同步（用户已确认） |
| 2 | 固定 2 人房间 | 用户确认只做 2 人，可以简化结算、房主和中途加入的逻辑 |
| 3 | 不支持手机，只做键盘操作；音效放在 P1 | 用户确认 |
| 4 | 服务器权威，客户端只发方向意图，服务器以 12 Hz 广播全量快照 | 从根本上避免作弊和两端不一致；全量快照对丢包和乱序天然免疫，256 格的数据量很小 |
| 5 | 技术栈：Node + TypeScript + Express + Socket.IO，前端用 Vite + 原生 TS + Canvas | Socket.IO 自带房间、重连和心跳，最省时间；视图很少，不需要框架 |
| 6 | 单服务部署：生产环境由 Express 托管 vite build 的产物，同源提供 WebSocket | 不需要处理 CORS 和 Origin 配置，一个平台、一个进程就能上线 |
| 7 | 开发模式：Vite（5173）通过代理把 /socket.io、/api、/healthz 转发到后端（3000），`npm run dev` 一条命令同时启动前后端 | 前端可以热更新，同时与生产环境保持同源结构一致 |
| 8 | 生产环境直接用 tsx 运行 TS 服务端，不单独编译 | 省掉服务端构建配置，以节省时间；代价是启动略慢，这里可以接受 |
| 9 | 构建所需的工具（vite、typescript、tsx）放在 dependencies 中 | 部署平台在 NODE_ENV=production 下安装依赖时可能跳过 devDependencies，放在 dependencies 可以避免构建失败 |
| 10 | 重连 token 存 sessionStorage，昵称存 localStorage（DESIGN.md 已同步更新） | 面试官很可能在同一个浏览器里开两个标签页自测；如果 token 用 localStorage，两个标签页会共用同一个座位并互相挤掉 |
| 11 | 增加 `/healthz` 健康检查和 `npm run smoke` 冒烟脚本（双客户端强制走 WebSocket） | 部署平台需要健康检查；脚本提供可复制运行的验收命令，并能在公网验证 wss 是否可以穿透代理 |
| 12 | 阶段 1 的"首次部署"先用沙箱临时公网地址验证，随后正式部署到 Render：https://paint-rush.onrender.com | 先用临时地址打通 HTTPS 代理加 wss 链路，用户确认平台后再正式上线；正式地址已经替代临时地址 |
| 13 | 正式部署平台定为 Render（用户确认），由 Agent 通过 Render 连接器（API key）创建服务、部署和查看日志；区域选新加坡，免费套餐，构建命令 `npm install && npm run build`，启动命令 `npm start` | 部署是风险最高的一环，Agent 能直接查看日志并排查问题，不需要用户转述；新加坡离用户最近 |
| 14 | 代码托管在 GitHub 公开仓库 lytruby/paint-rush，按阶段提交并推送；Render 服务 paint-rush（srv-dbbi07k9v7es73fagjag）；自动部署实际没有生效（见 ISSUES #7），改为每个阶段推送后由 Agent 手动触发部署 | 用户确认使用 GitHub 连接器，并选择公开仓库：Render 需要能读取仓库，面试官也需要能看到代码；自动部署让后续每个阶段推送后都能直接在正式地址验收 |
| 15 | `room` 消息增加 `phaseRemainingMs`（服务器发出时刻的剩余毫秒数），客户端用"收到时刻 + 剩余时间"推算倒计时结束点 | 不依赖两端时钟一致；两端网络延迟差就是倒计时误差（实测本地 0ms），不需要单独做时钟同步 |
| 16 | 通过邀请链接打开房间时，先 GET 预检，再显示"加入房间"确认卡片（可以修改昵称）；从首页创建或输入房间码进入时则直接入座 | 受邀者可以先确认身份并修改昵称；满员或房间不存在可以在加入前就提示；创建者少点一次 |
| 17 | 阶段 2 的临时规则：任何人离开或断线都立即移除座位；如果当时不在大厅，就取消当前阶段并回到大厅；客户端重连后用新座位重新加入 | 先保证房间状态一致、不会卡死；阶段 4 再替换为 token 恢复原座位、15 秒掉线保留和对局中离开提前结算 |
| 18 | 房主离开后自动转给剩下的玩家；空房间（包括创建后没人加入的房间）60 秒后回收，每 10 秒扫描一次 | 实现成本只有几行；如果不这样做，大厅会在房主离开后卡死，内存也会泄漏 |
| 19 | 房间码使用 4 位字符，去掉了容易混淆的 I、O、0、1；房间码大小写不敏感；昵称在服务端过滤控制字符并截断到 12 字符，客户端渲染时统一做 HTML 转义 | 方便口头报房间码；防止 XSS 和异常输入 |
| 20 | tick 频率从 12 Hz 改为 10 Hz（每 tick 最多走一格，也就是每秒 10 格） | 16×16 的棋盘上，每秒 12 格太快，1.3 秒就能横穿全图，很难控制；10 Hz 加上客户端插值，看起来同样平滑 |
| 21 | 输入采用"按住方向 + 本 tick 内按过的方向"两个字段：短按（在两个 tick 之间按下又松开）也至少走一格；客户端忽略系统按键重复（e.repeat），只在方向变化时发送 | 短按不会丢；连按或长按都不会超过每 tick 一格 |
| 22 | 碰撞规则对双方对称：目标格是对方当前所在格，或者双方目标是同一格时，都原地不动 | 规则结果与服务器处理两人的先后顺序无关，不会出现先处理的一方占便宜 |
| 23 | 倒计时开始时就初始化本局并下发快照；房间内的 tick 跨局单调递增 | 倒计时期间就能看到棋盘和出生点；客户端可以统一用"tick 不大于当前的就丢弃"来处理乱序 |
| 24 | 倒计时期间就开始记录按键，进入对局的那一刻自动补发一次当前方向 | 玩家可以提前按住方向键，开局第一帧就开始移动 |
| 25 | 阶段 3 验收脚本改为对延迟不敏感：等到位移出现（超时 3 秒），不再固定等待；"互相看到"改为比较双方都收到的同一 tick；碰撞测试按两人的实际相对位置决定相向方向，并接受对峙（间距 1 或 2）。另外新增 `npm run latency` 诊断脚本 | 第一次对正式地址验收时有 3 项失败，原因是沙箱到 Render 的 RTT 约 470ms，固定等待太短；本地 16 项全部通过，说明游戏逻辑没有问题 |
| 26 | 接受对称碰撞规则带来的"对峙"：两人相隔一格并同时冲向中间那格时，双方都被挡住，直到有一方换方向 | 这是公平规则的自然结果（谁也不占先），而且只要换个方向就能解开；如果改成先到先得，就要依赖输入到达服务器的先后，网络好的一方会占便宜 |
| 27 | 所有生命周期变化集中在 rooms.ts 的 joinRoom / markDisconnected / removePlayer / voteRematch 四个函数，每次变化后广播完整房间状态 | 对应 DESIGN 风险 2：刷新、掉线、离开、再来一局交叉发生时，只需要推理这几个函数 |
| 28 | 断线（disconnect）只标记掉线并保留 15 秒，主动离开（leave）才立即释放座位；只有"当前连接就是该座位的连接"时，断线才生效 | 刷新会产生一次断线，不能被当成离开；被新标签页踢掉的旧连接断开时，不能把已经恢复的座位标成掉线 |
| 29 | 重连恢复座位时重置 lastSeq | 新页面的输入序号从 1 开始，不重置的话，刷新后的所有输入都会被当成旧包丢弃（验收脚本专门覆盖） |
| 30 | 同一 token 出现新连接时，旧连接收到 REPLACED 并被移出房间，而不是直接断开 socket | 复制标签页会连 sessionStorage 一起复制，两个页面会争同一个座位；明确提示比静默断开更好理解 |
| 31 | 对局中离开时，先结算（离开者的分数保留在结果里），再移除座位；结算页只剩一人时停在结算页，新玩家加入后才回到大厅 | 剩下的一方能看到完整的结果和"对手离开"的原因，而不是突然被弹回大厅 |
| 32 | 客户端缓存见过的玩家（昵称和颜色槽位） | 对手离开后，棋盘、HUD 和结算仍用他原来的颜色和昵称显示（走查时发现离开者被画成了己方颜色） |
