**v2 变更记录**

- 人数固定为 2 人。
- 不支持手机，只做桌面端键盘操作。
- 音效保留在 P1，收尾有空再做。
- 不交付录屏和单独的设计文档，设计说明并入 README。
- 新增"面试交付物"一节（第 5 节）。

**开发期变更记录**

- 阶段 1：重连凭证 token 从 localStorage 改为 **sessionStorage**（按标签页隔离，刷新后仍保留）。原因：面试官很可能在同一个浏览器里开两个标签页自测，如果用 localStorage，两个标签页会共用同一个 token，第二个标签页会把第一个挤掉。昵称仍存 localStorage。
- 阶段 3：tick 从 12 Hz 改为 10 Hz（移动速度为每秒 10 格）；短按也至少走一格；碰撞规则对双方对称；倒计时期间就显示棋盘和出生点。
- 阶段 4：错误码增加 `REPLACED`（同一座位在另一个标签页恢复时，旧页面收到它并显示"已在别处打开"）；对局中有人离开时，结算里仍保留离开者的分数；结算页只剩一人时，新玩家用同一链接加入后房间回到大厅；重连时服务器重置该座位的输入序号（新页面的 seq 从 1 开始）；掉线的玩家在大厅中同样保留 15 秒。
- 阶段 2：`room` 消息增加 `phaseRemainingMs` 字段（倒计时和对局的剩余毫秒数），用于两端同步倒计时；错误码增加 `NOT_READY`（人没到齐时点开始）；通过邀请链接进入时，先显示"加入房间"确认卡片（可以修改昵称）。

## 0. 玩法

网格涂色对战（已确认）。两名玩家在 16×16 网格上移动，走过的格子染成自己的颜色，也可以把对手的格子抢回来。60 秒后占地多的人获胜。

---

## 1. 一句话目标

做一个打开链接就能玩的浏览器实时 1v1 对战小游戏：双方通过房间链接进入同一局，60 秒内比谁涂的地盘多，结果由服务器统一判定，支持掉线重连和再来一局。

## 2. 功能范围

### P0 必做

| 模块 | 内容 |
|---|---|
| 进入体验 | 无需账号。首页填写昵称（默认随机生成，存在 localStorage），点击"创建房间"后生成 4 位房间码和邀请链接 `/r/ABCD`；对方打开链接或输入房间码即可加入 |
| 房间大厅 | 显示双方的颜色和昵称，提供"复制邀请链接"按钮；两人到齐后房主可以点击"开始" |
| 开局 | 服务器广播 3-2-1 倒计时，双方同时开始 |
| 核心玩法 | 用方向键或 WASD 移动，按住时每个 tick 前进一格，走过的格子染成自己的颜色；两人不能站在同一格，相撞时被挡住；每局 60 秒 |
| 实时同步 | 采用服务器权威：客户端只发送方向意图，位置、涂色、计时和胜负全部由服务器计算，并以固定频率广播全量快照 |
| HUD | 显示剩余时间和双方的实时占地百分比 |
| 结束 | 时间到后由服务器结算，弹出胜者或平局横幅，双方看到的结果一致 |
| 再来一局 | 双方都点击"再来一局"后进入倒计时，棋盘重置；按钮上显示"对方已准备" |
| 生命周期 | 刷新后自动回到原座位；掉线时保留座位 15 秒并显示"掉线中"；主动离开或掉线超时会让对局提前结束，剩下的一方获胜；满员时第三人看到"房间已满"提示；房间空置 60 秒后销毁 |
| 基础反馈 | 涂色时有颜色过渡，最后 10 秒计时变红，结算时显示胜利或失败横幅 |

### P1 加分（P0 全部稳定后，在收尾阶段视情况做）

1. 用 Web Audio 合成音效（倒计时、涂色、结束）
2. 本地预测己方角色位置，并由服务器校正
3. 显示 Ping 值
4. 满员时第三人以观战方式进入

### 明确不做

- 账号和登录、数据库持久化
- 随机匹配、排行榜和战绩
- 聊天和语音
- 道具和技能、AI 机器人、皮肤
- 多实例部署和水平扩展
- 超过 2 人的房间
- **手机和触屏适配**
- 录屏和单独的设计文档

## 3. 页面清单

只有 2 个路由。房间内通过 status 切换视图，不做页面跳转。

| 页面或视图 | 路由 | 内容 | 主要操作 |
|---|---|---|---|
| 首页 | `/` | 游戏名、一句话规则、昵称输入框 | 创建房间；输入房间码加入 |
| 房间：大厅 | `/r/:code`（status 为 lobby） | 房间码、邀请链接、两个玩家槽位（颜色、昵称、房主标记、在线状态），以及"等待对手加入…"提示 | 复制链接；房主点击开始（两人到齐后才可点）；离开 |
| 房间：倒计时 | 同上（countdown） | 棋盘、出生点、大号 3-2-1 | 无 |
| 房间：对局中 | 同上（playing） | Canvas 棋盘、剩余时间、双方占地百分比、掉线标记 | 方向键或 WASD 移动；离开 |
| 房间：结算 | 同上（ended） | 胜负或平局横幅、双方百分比、对方是否已准备 | 再来一局；返回首页 |
| 异常浮层 | 全局 | 房间不存在、房间已满、连接中断正在重连、对手已离开 | 返回首页或重试 |

## 4. 数据结构与 API

### 4.1 数据结构

所有数据都存在服务器内存中，不使用数据库。

**Room（房间）**

| 字段 | 类型 | 说明 |
|---|---|---|
| code | string(4) | 主键 |
| hostId | string | 房主的 playerId |
| status | enum | `lobby` / `countdown` / `playing` / `ended` |
| players | Player[]（长度不超过 2） | 下标 0 和 1 即 slot，对应颜色 |
| grid | Uint8Array(256) | 0 表示无人占领，1 和 2 表示对应 slot 的玩家 |
| tick | number | 单调递增的帧号 |
| phaseEndsAt | number | 当前阶段结束的服务器时间戳 |
| round | number | 当前局数 |
| rematchVotes | Set\<playerId\> | 已点击"再来一局"的玩家 |
| emptySince | number \| null | 用于判断何时销毁空房间 |

**Player（玩家）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | 公开 ID |
| token | string | 私密的重连凭证，只发给本人，存在 sessionStorage（按标签页隔离，刷新不丢） |
| name | string | 昵称，最多 12 个字符 |
| x, y | number | 网格坐标 |
| dir | `up` / `down` / `left` / `right` / null | 当前的方向意图 |
| lastSeq | number | 已处理的最大输入序号 |
| connected | boolean | 是否在线 |
| disconnectedAt | number \| null | 掉线时间，超过 15 秒即视为离开 |
| socketId | string | 当前连接；同一 token 出现新连接时，踢掉旧连接 |

**关系**：一个 Room 对应 1 到 2 个 Player。grid 中的值是 Player 在 players 数组中的下标加 1。

### 4.2 HTTP API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/rooms` | 创建房间，返回 `{ code }` |
| GET | `/api/rooms/:code` | 查询房间是否存在、当前状态和人数 |

### 4.3 WebSocket 事件

**客户端发给服务器**

| 事件 | 载荷 | 说明 |
|---|---|---|
| `join` | `{ code, name, token? }` | 加入房间；带 token 时视为重连 |
| `start` | `{}` | 仅房主可用，要求处于 lobby 状态且两人都在线 |
| `input` | `{ seq, dir }` | seq 不大于 lastSeq 的输入直接丢弃；每秒最多处理 20 条 |
| `rematch` | `{}` | 再来一局投票 |
| `leave` | `{}` | 主动离开 |

**服务器发给客户端**

| 事件 | 载荷 | 说明 |
|---|---|---|
| `joined` | `{ playerId, token, room }` | 只发给本人 |
| `room` | `{ code, status, hostId, players[], round, rematchVotes[], phaseRemainingMs }` | 元数据变化时广播；phaseRemainingMs 为当前阶段剩余毫秒数 |
| `snapshot` | `{ tick, status, remainingMs, players[{id,x,y,connected}], grid }` | 每秒 10 次全量广播（倒计时开始和结算时各补发一次）；客户端丢弃 tick 较旧的快照 |
| `over` | `{ scores[{id,cells,pct}], winnerId \| null, reason: 'time' \| 'opponent_left' }` | 结算；winnerId 为 null 表示平局 |
| `error` | `{ code, msg }` | 错误码：`ROOM_NOT_FOUND` / `ROOM_FULL` / `NOT_HOST` / `NOT_READY` / `BAD_REQUEST` / `REPLACED` |

### 4.4 同步与反作弊

| 问题 | 处理方式 |
|---|---|
| 状态由谁决定 | 服务器决定一切；客户端只负责渲染和发送意图 |
| 延迟 | 服务器以 10 Hz 的固定 tick 推进；客户端对角色位置做插值，让移动看起来平滑 |
| 重复操作 | 按 seq 去重；每个 tick 每人最多移动一格，连续按键不会加速 |
| 乱序 | 丢弃 seq 较旧的输入和 tick 较旧的快照；由于每次发的都是全量快照，丢包后下一帧会自动恢复 |
| 作弊 | 客户端无法提交坐标或分数；服务器校验越界、碰撞和移动速度；对输入限流 |
| 两端结果不一致 | 每一帧都用服务器快照覆盖本地状态，结算只以服务器下发的 `over` 为准 |

### 4.5 生命周期

| 场景 | 行为 |
|---|---|
| 刷新 | 用 token 自动重新 `join`，恢复原座位，并回到当前阶段的视图 |
| 掉线 | 角色停在原地，显示"掉线中"；15 秒内重连即可恢复 |
| 主动离开或掉线超时（大厅中） | 释放座位，大厅回到"等待对手"状态 |
| 主动离开或掉线超时（倒计时或对局中） | 立即结算，剩下的一方以 `opponent_left` 为由获胜 |
| 主动离开或掉线超时（结算页） | 清空再来一局的投票，剩下的一方回到大厅等待新对手 |
| 中途加入 | 有空座时直接入座（例如一方离开后，新玩家可以用同一个链接进来）；满员时提示"房间已满" |
| 房主离开 | 剩下的一方自动成为房主 |
| 重复连接 | 同一 token 建立新连接时，断开旧连接 |
| 再来一局 | 双方都投票后，重置棋盘和出生点，局数加 1，进入倒计时 |
| 空房间 | 无人在线满 60 秒后销毁 |

| 优先级 | 产物 | 要求 |
|---|---|---|
| 1 | **线上可玩地址** | 面试官最可能的测试方式，是在两个浏览器窗口里打开同一个链接自己对战，所以必须做到点开就能玩。提交前自己先打开一次唤醒服务，确保不需要等待冷启动 |
| 2 | **GitHub 仓库** | 克隆后用 `npm i && npm run dev` 一条命令就能本地启动。按开发阶段分别提交（骨架 → 房间 → 玩法 → 生命周期 → 收尾），让 git 历史本身体现开发过程 |
| 3 | **README** | 这是体现思考深度的主要载体，结构见下方 |

**README 结构**

1. 在线地址和一句话玩法说明
2. 两人对战的快速上手：A 创建房间并复制链接，B 打开链接，A 点击开始
3. 本地运行方法
4. 架构简图（文字或 ASCII 即可）
5. 对题目中四个思考点的回答。这是重点，可以直接复用本文档的内容：
   - 进入体验：免账号、链接邀请
   - 玩法与反馈
   - 实时同步：第 4.4 节
   - 生命周期：第 4.5 节
6. 取舍与已知限制：例如只支持单实例、状态存在内存中（服务重启后房间丢失）、没有做客户端预测
7. 如果有更多时间会怎么做：例如客户端预测、观战、匹配、持久化

## 6. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 服务端 | Node.js、TypeScript、Express、Socket.IO | 自带房间、重连和心跳；Express 同时托管前端构建产物，实现单服务部署 |

| 部署 | **已确定：Render**（新加坡区域，免费套餐，单实例，每个阶段推送后手动触发部署），地址 https://paint-rush.onrender.com | 平台必须支持 WebSocket 长连接，不能用 Vercel 这类 serverless 平台。如果选择会休眠的免费套餐，要在提交前唤醒服务，并在 README 中说明首次访问可能需要等待 |

## 7. 开发阶段（总计 60 分钟）

| 阶段 | 时间 | 内容 | 验收标准 |
|---|---|---|---|
| ① 骨架和首次部署 | 0–8 分钟 | 建立仓库，搭好 Express、Socket.IO 和 Vite，定义 shared 协议；**把空骨架部署上线一次** | 本地两个标签页都能连上服务器；线上地址能打开页面，并且能建立 WebSocket 连接 |
| ② 房间 | 8–20 分钟 | 首页、创建和加入、大厅、复制链接、开始、倒计时、满员和房间不存在的提示 | A 创建房间后，B 打开链接，双方都能看到对方；房主点击开始后，两端同时进入倒计时；第三人看到"房间已满"；错误的房间码有提示 |
| ③ 玩法 | 20–35 分钟 | tick 循环（移动、碰撞、涂色、计时）、快照广播、Canvas 渲染和插值、HUD、结算 | 双方都能移动，并实时看到对方；涂色和占比在两端一致；60 秒后两端显示相同的胜负结果；连续按键不会加速 |
| ④ 生命周期 | 35–40 分钟 | token 重连、15 秒掉线保留、离开后提前结算、房主转移、再来一局 | 对局中刷新后能回到原位继续玩；关闭一端后，另一端显示"掉线中"，超时后判对手获胜；双方点击"再来一局"能开始新的一局 |
| ⑤ 收尾 | 40–60 分钟 | 正式部署，并用两台设备在不同网络下测试（6 分钟）；打磨手感和视觉，有余力再加音效（6 分钟）；写 README（6 分钟）；机动时间（2 分钟） | 通过线上链接完整跑通"加入 → 开始 → 游玩 → 结束 → 再来一局"；README 包含第 5 节的全部内容；git 历史按阶段提交 |

**时间不够时的砍需求顺序**：先砍全部 P1，再把房主转移简化为"任何人都能点开始"，最后去掉涂色过渡动画。核心闭环和服务器权威同步不能砍。

## 8. 风险最高的 3 个点

1. **部署和公网环境**
   - 风险：平台对 WebSocket 的支持情况、冷启动、wss 和代理超时，这类问题只有上线后才会暴露。
   - 对策：在阶段 ① 就把空骨架部署上线，提前打通整条链路。

2. **生命周期状态机**
   - 风险：刷新、掉线、离开和再来一局交叉发生时，容易出现幽灵玩家、对局卡死、视图停留在错误阶段等问题。
   - 对策：所有状态变化都集中在服务器的少数几个函数里处理；每次变化后广播完整的状态，客户端只根据收到的状态渲染。

3. **真实网络下的手感**
   - 风险：纯服务器权威的方案在高延迟下会有明显的操作迟滞。
   - 对策：P0 阶段先用插值，tick 定为 10 Hz（12 Hz 在 16×16 棋盘上移动太快）；如果公网测试发现手感差，收尾阶段优先做本地预测。
